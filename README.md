# 🖥️ The OS Museum

**Interactive, in-browser simulations of classic operating systems — each one a single, self-contained HTML file.**

Nothing real runs. No VMs, no emulated CPUs, no ROMs, no installs. Every exhibit is a front-end
re-creation of the look, feel and quirks of a beloved OS: a museum piece you can actually click on.

## 🚀 Getting started

**Visit the museum online:** [tunlezah.github.io/os-emu](https://tunlezah.github.io/os-emu/) — every exhibit, served straight from this repository via GitHub Pages.

Or run it locally — there is nothing to build and nothing to serve.

1. Clone or download this repository.
2. Open **[`index.html`](index.html)** in any modern browser — straight from disk (`file://`) works fine.
3. Pick an exhibit and boot it.

You can also open any exhibit's `.html` file directly; each one is fully standalone.

| 1981 | **Xerox 8010 Information System (Star)** | Xerox | [`star.html`](star.html) | The machine almost everything on your screen came from, and the only exhibit here that is an argument about *your* computer. 1024 × 808 pixels, one bit deep, 72 dots to the inch: no greys except dither, no colour, nothing antialiased, on a Desktop that is 14 × 11 squares of one inch — 154 places for an icon, exactly as Star's designers described it. The mouse has **two** buttons, SELECT and ADJUST, and there is no third and no context menu, because Star's designers built six different mouse designs and argued in print that three was too many and one too few. Everything is **noun then verb**: select the thing, then press the key. And the keys are the point. Nine of them, on the housing under the screen, doing the same nine things to every object in the system — a character, a paragraph, a line inside a drawing, a table column, a record, an icon, a folder, a printer, a directory entry, a window, a property sheet, and the Desktop itself. | 1989 | **Atari TOS 1.04 + GEM** | Atari | [`ataritos.html`](ataritos.html) | The only exhibit here that is a **controlled experiment**. Digital Research shipped GEM for the IBM PC in February 1985 with overlapping windows, icons on a desktop, a trash can and window animations; Apple sued; Digital Research **settled — it did not lose a trial —** and GEM Desktop 2.0 arrived on 24 March 1986 with the windows locked into two fixed panes, the icons gone from the desktop and the trash can gone with them. The GEM Atari shipped in ROM, from the same code and the same year, kept all of it for the machine's entire commercial life. So this exhibit ships **both**: `atari` (TOS 1.04, whose AES reports itself as 1.4) and `pcgem2` (GEM Desktop 2.0), running on **one** desktop shell, **one** widget toolkit and **one** disk, with only a rule set between them — and an audit in the guide that fails loudly if a rule differs without a museum label to explain it. Three views: single, **side by side** with both machines on the same filesystem so a file you drag on one vanishes from the other, and **diff**, which drops numbered markers on all **thirteen** documented differences. Try to drag a window in the PC variant: nothing happens, and nothing was supposed to. Round the back it is a real ST. Choose your monitor at power-on and the choice constrains you — the SM124 does 640×400 mono and nothing else, the colour monitor does 320×200 in 16 of 512 and 640×200 in four and never high — and low resolution is where you feel that GEM was designed for the big screen. TOS is in ROM, so the desktop arrives in about two seconds and the guide times it against the PC booting DOS and then GEM off a disk. **Menus drop on hover**, not on click, because Digital Research shipped them that way and even added a preference whose default is the hover setting. The busy pointer is **the bee**. Names are eight-and-three and upper case, A: and B: are floppies and C: is a hard disk, `DESKTOP.INF` is a text file that is really parsed — edit the `#M` and `#T` lines in SCRIBE and the drive icons and the trash move on the next boot — the root of the boot disk holds **seven** `.ACC` files and the machine loads six, and the item selector has TOS 1.04's row of sixteen drive buttons and every one of its remaining annoyances. | 1992 | **RISC OS 3.11** | Acorn | [`riscos.html`](riscos.html) | The desktop that made different choices, and was right about several of them. There is **no menu bar** — not on the screen, not in the windows, nowhere — because every menu in the entire system is opened with the **middle mouse button** over whatever you are pointing at, appears at the pointer, and is gone when you leave it. The three buttons are the interface and the vocabulary is specific: **Select** picks things up, **Menu** produces the menu for whatever is under it, and **Adjust** is the modifier — it extends a selection, scrolls the *other* way, opens a directory while closing its parent, and chooses a menu item while **leaving the menu on the screen**, which you will understand about four seconds after trying it on Display → the four sort orders. Then the moment the exhibit is arranged around: write something in **!Edit**, choose Save, and you are handed a small box containing a file icon, an editable name, no path field and no button that obviously means yes. You will hesitate. Then you will drag the icon into a directory display and the file will be there. Underneath is a **real message protocol** — DataSave, DataSaveAck, DataLoad, DataLoadAck, and RAMFetch/RAMTransmit when two applications can move the data between themselves without a file existing at all — and the guide's live log shows the conversation as you cause it, because drag-to-save, drag-to-load and app-to-app transfer are the same handshake with different participants. Applications are **directories** whose names begin with `!`: Shift-double-click one and the illusion drops, revealing `!Run`, `!Boot`, `!Sprites` and `!RunImage` as ordinary readable files; you install one by copying it and remove it by deleting it, in ROM, in 1989. `!Boot` runs because the Filer has **seen** the application, so open `$.Apps` and watch !Sundial's icon change from generic to its own in front of you — and then watch a file elsewhere on the disc acquire an icon too, because that `!Boot` just registered file type **&1E6**, which nobody in the world has ever used. File types are **twelve bits of metadata**, not suffixes: `*SetType` a text file to Sprite and the Filer redraws before you have pressed anything else. Paths use `.` and `$` and `^` (`ADFS::HardDisc4.$.Documents.Letter`), discs are **named rather than lettered**, and `Resources:$` is the ROM presented as a filing system you can walk into — where `Resources.Wimp.Sprites` opens in **!Paint** and holds the desktop's own icons, so painting on `file_fff` changes every text file on the screen while you watch. The **Task display** draws every application's memory allocation as a bar and lets you **drag it while the program runs**: pull the RAM disc bar and `RAM::RamDisc0` appears on the icon bar, pull screen memory down and the modes you can no longer afford vanish from the list, pull free memory and something complains. **Interactive Help** is one system service, not a table of strings, so it describes window furniture, menu entries, individual files, memory bars and — point it at itself — the help window. `f12` gives the `*` prompt over the running desktop with forty commands behind it, and `*BASIC` gives **BBC BASIC V with an ARM assembler inside it**: `$.Programs.ArmDemo` opens a square bracket in the middle of a numbered line, assembles ARM machine code in two passes and calls it, on a home computer, in 1992 — the same argument the [Commodore 64](c64.html) exhibit makes about a BASIC in ROM, taken one step further. Also !Draw and DrawFiles, !Paint, !Maestro through a multi-channel synth, !Alarm as a clock with no window, !Chars, !Configure and CMOS RAM, the Pinboard, iconising windows onto it, six screen modes **by number** including mode 12's famously tall pixels, and a cooperative poll loop demonstrated honestly: freeze the desktop from the guide and only the pointer keeps moving, because that was a hardware sprite. Flat RISC OS 3.1x furniture throughout, a hatched title bar on the focused window only, an 8×8 bitmap system font, and every sprite drawn from scratch — the mark on the Task Manager's icon bar icon is an **original placeholder** standing where Acorn's logo sat. Not a memorial either: RISC OS 5 was open-sourced in 2018, is maintained by RISC OS Open, and runs on the Raspberry Pi — and the instruction set Acorn designed for this machine is very probably in the device you are reading this on |

## ✨ How the exhibits are built

Every simulation in this museum follows the same rules:

- **One file.** All HTML, CSS and JavaScript live in a single `.html` document.
- **Zero dependencies.** No CDNs, no frameworks, no network requests, no assets to load.
- **Offline-first.** Opening the file from disk is the supported way to run it.
- **Simulation, not emulation.** These pages re-create interfaces and behaviour in the browser;
  they don't execute original software or contain any copyrighted binaries. Where an exhibit
  goes deeper — the C64's BASIC interpreter, its video chip, its sound chip and its 6510,
  TempleOS's HolyC compiler and its DolDoc engine, or RISC OS's Wimp, its data transfer
  protocol and its BBC BASIC with an ARM assembler — every byte of it is written from
  scratch to behave like the real thing.

The landing page ([`index.html`](index.html)) follows the same rules and renders its gallery
from a small data array, so the museum grows without any structural changes.

## ➕ Adding a new exhibit

New wings are always welcome. To add an OS:

1. **Create the simulation** as a single self-contained file, e.g. `riscos.html`, following
   the rules above (one file, no external resources, works from `file://`).
2. **Register it in the gallery** — open [`index.html`](index.html) and append one object to the
   `EXHIBITS` array near the top of the `<script>` block:

   ```js
   {
     file:   "riscos.html",
     name:   "RISC OS 3.11",
     vendor: "Acorn",
     year:   1992,
     glyph:  "!Boot",                      // shown on the card's mini screen
     desc:   "The icon bar, three mouse buttons and a filer that means it.",
     accent: "#f0c000",                    // card accent colour
     bg:     "#2a2a3a",                    // mini-screen background
     tags:   "acorn risc os arm archimedes"  // extra search keywords
   },
   ```

   Search, sorting and the card grid pick it up automatically — no other changes needed.
   If one exhibit ships several builds, add an optional `variants: [{file, label}, …]`
   array to the entry — the card then shows one launch link per build (see NetWare).
3. **Add a row** to the exhibits table in this README.
